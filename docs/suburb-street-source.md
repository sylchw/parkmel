# Street geometry and suburb imports

Coverage is generated by code from OpenStreetMap geographic coordinates, not by manually tracing a picture or reading signs. Geometry gives contributors a place to attach parking interpretations; it is not evidence that parking is allowed.

## Current coverage

Carnegie plus Chadstone, Bentleigh, Brighton, Malvern, Oakleigh, Clayton, Springvale, Mulgrave, Clayton South, Moorabbin, Hampton, St Kilda, Glen Waverley, Malvern East, Oakleigh South and Hawthorn. There are 59,270 distinct street-side targets. The original 3,246 Carnegie targets and IDs are preserved unchanged.

The expansion uses the dated [Geofabrik Victoria extract](https://download.geofabrik.de/australia-oceania/australia/victoria.html), `victoria-261006.osm.pbf`. Its filename and SHA-256 are recorded in `public/coverage/manifest.json`. The dated download is `https://download.geofabrik.de/australia-oceania/australia/victoria-261006.osm.pbf`. Input extracts and Python runtimes stay in ignored `work/`; they are not shipped to visitors.

## How it works

1. `scripts/import-suburb-roads.py` streams the extract with pyosmium. It resolves each named suburb's admin-level-9 polygon, checks geometry validity and selects supported road ways intersecting those polygons. It writes intermediate boundaries and roads to ignored `work/suburb-import/`.
2. `scripts/build-suburb-sections.mjs` splits ways at shared coordinate junctions and way boundaries, then produces deterministic left/right IDs. Existing Carnegie way IDs are excluded from the new generation so existing drafts and publications retain their targets.
3. The generated manifest includes suburb polygons. Each suburb has its own GeoJSON file, fetched only when selected. Whole intersecting ways are retained at suburb edges rather than clipped into competing IDs. Border targets may appear in more than one suburb file with the same ID.
4. `data/coverage-sections.json` is the trusted server registry used to validate annotation targets. It is traced into the annotation API deployment and is not fetched as a single browser download.
5. Migration 011 registers coverage boundaries and supports either the existing geometry schema or optional normalized migration 010. Migration 012 registers new targets additively in bounded batches. The importer has no grants to anonymous, authenticated or service-role clients. Existing street rows are not changed. Migration 013 replaces the old draft rectangle constraints with a broad coordinate guard plus a private trigger enforcing exact registered coverage polygons. Ownership, verified-email eligibility and RLS remain enforced.

Two side targets are generated from each centerline; this does not assert that both sides permit parking or that every divided road is represented perfectly. The extract also includes unnamed and service ways, including driveways and parking aisles. These are geographic targets requiring filtering or contributor review, not a classification of public parking frontage. Junction topology also needs contributor review. Check signs and the actual road side before annotating. No parking schedules or verified publications are created by this import.

## Repeatability and checks

Rebuild in this order, from the repository root, using an isolated Python environment with the versions listed in the importer:

```sh
python scripts/import-suburb-roads.py work/suburb-import/victoria-261006.osm.pbf
node scripts/build-suburb-sections.mjs
node scripts/build-suburb-migrations.mjs
```

 The scripts require the intermediate files in their documented locations. Generate sections before generating migrations. Keep existing target IDs stable; do not replace a published registry casually when updating OSM data.

`npm test` checks coverage, legacy identity preservation and trusted lookup. `npm run test:db` exercises the normalized schema; `node tests/db/run.mjs --legacy-geometry` exercises the current hosted schema without migration 010. Both test fresh isolated databases, geometry integrity, registration counts and importer access restrictions. Browser checks exercise suburb switching without replacing the map canvas.

## Next scaling hurdle

The first implementation hurdle was the fixed Carnegie boundary and registry; that is now removed for these suburbs. Moderation, sign evidence and reliable email delivery remain the practical prerequisites for real contributions. For much larger coverage, replace per-suburb GeoJSON with viewport or vector-tile delivery, benchmark the server registry and database size, and review OSM updates without invalidating published targets. Self-hosting Photon addresses search availability separately from parking geometry.
